Three hashicorp/raft Bugs

What deterministic simulation testing found in hashicorp/raft, explained for someone who knows Raft from the paper but not this library: what goes wrong, why the code is the way it is, how the fix works, and how the simulation found, reproduced and checked each one.

1. A live majority that can never elect a leader

Liveness, permanentSince 6b4e320 (PR #526, 2022)Branch fix/stale-config-vote

The Raft you need for this

  • Elections. A server that hears nothing from a leader becomes a candidate for a new term and asks the others for votes. It wins with votes from a majority of the voters. Each server votes at most once per term.
  • The election restriction (paper §5.4.1). A voter refuses a candidate whose log is less up to date than its own: compare the last entries' terms, then their indexes. This is what keeps committed entries safe across leader changes.
  • Pre-vote (on by default here). Before a real election, a candidate asks "would you vote for me?" without raising anyone's term. Only if a majority says yes does it start the election. This stops a server that was cut off from disrupting the cluster when it comes back.
  • Membership changes go through the log one server at a time: add a voter, add a non-voter, promote, demote, remove. A server uses the latest configuration in its own log, committed or not. So a server that missed some log entries also has an old idea of who the voters are.

What hashicorp added, and why

Plain Raft never asks whether the candidate is a member: a voter checks the term and the logs, nothing else. In 2022 a user hit a problem (#524). A server was removed or demoted while cut off, so it never learned it had lost its vote. It kept starting elections with ever higher terms, and the real cluster kept stepping down to follow those terms. PR #526 made each server reject a vote or pre-vote request from a candidate that isn't a voter in the receiver's latest configuration. For that case it works: the removed server is ignored.

The flaw: the receiver judges the candidate by its own latest configuration, and if the receiver is the one that's behind, that configuration is out of date.

The sequence

Everything in it is ordinary: one network partition, one routine replacement of a server (add the new one, then remove the old one), and one server that dies for good. The partition and the replacement are unrelated; they just overlap.

Plain Raft would recover at once: C would check only that D's log is at least as up to date as its own (it is), grant the vote, and D would win and send C the newer configuration. The bug is the membership check, not the protocol.

The fix

Trust your configuration to judge a candidate only when your log isn't behind the candidate's. If the candidate's log is ahead of yours, it may know configuration changes you haven't seen, in which it is a voter, so skip the membership check and let Raft's ordinary rules decide.

Why the fix is safe, and why it keeps #524's protection

  • Safety. The fixed rule only ever grants votes that plain Raft would also grant: it still runs Raft's own checks, and only sometimes skips the extra one. Raft is safe without the membership check, so it is safe with it applied less often.
  • When the logs are equal, the check is still applied, and it is accurate there. Two logs with the same last term and index are identical (Raft's Log Matching property), so the two servers hold the same configuration.
  • The #524 case is a server that missed its own removal or demotion. Its log is behind the cluster's (it never received those entries), so the check still applies and it is still rejected.
  • Caveat. That last point is an argument, not a measurement. The simulation's membership sweep also passes with the checks removed entirely, so it doesn't exercise #524's disruption. A scenario for it (a removed server campaigning) is planned.

The code change is small: a helper and one extra condition on each of the four checks (two in requestVote, two in requestPreVote).

func (r *Raft) candidateLogIsAhead(lastLogTerm, lastLogIndex uint64) bool {
	lastIdx, lastTerm := r.getLastEntry()
	return lastLogTerm > lastTerm || (lastLogTerm == lastTerm && lastLogIndex > lastIdx)
}

if len(r.configurations.latest.Servers) > 0 && !hasVote(r.configurations.latest, candidateID) &&
	!r.candidateLogIsAhead(req.LastLogTerm, req.LastLogIndex) {
	r.logger.Warn("rejecting pre-vote request since node is not a voter", "from", candidate)
	return
}

How the simulation found it, pinned it down, and checked the fix

  1. Found. The membership sweep (1 to 7 voters, an operator adding, promoting, demoting and removing servers, servers lost for good, crashes, partitions) failed its check that "the cluster recovers": no leader 5 seconds after the faults ended, with a majority alive. I named the wrong cause twice, before raft's own log showed C's rejection on the pre-vote path.
  2. Pinned down. A scripted test (TestDSTStaleConfigStall) plays the exact sequence with seeded timing. On correct raft, 15 of 20 seeds stay leaderless forever. With only the membership checks switched off, 20 of 20 recover. That isolates the cause. The other 5 seeds recover on correct raft too, and I haven't analyzed why.
  3. Seen again, unscripted. The sweep with gray failure (slow and lossy links) hit it with no planned partition: a voter lagging behind lossy links kept a configuration without the candidate and rejected it after the leader was lost (seed 175).
  4. Fix checked. With the fix switched on: the scripted sequence recovers on 20 of 20 seeds, the membership sweep passes 200 of 200, and the gray membership sweep (with bug 2's fix too) passes 200 of 200. Every seed replays exactly, so any failure can be rerun with raft's own log.

2. A crash inside bootstrap strands a new server

Liveness, low severityOne write's window, once per serverBranch fix/bootstrap-crash

Background

A brand-new cluster has no leader to add members, so the first servers are bootstrapped: BootstrapCluster writes the initial configuration into the server's own log as entry 1 (term 1), and sets the stored current term to 1. Applications run the same thing at every start: "if HasExistingState says this server has no state, bootstrap it; then start raft".

HasExistingState says yes if the stored term isn't 0, or the log isn't empty, or a snapshot exists. The term counts on purpose. A server that has a term has taken part in some cluster, even with an empty log (a new member that voted before receiving entries), and bootstrapping it again could split it off into a second cluster.

The bug

BootstrapCluster writes the term first and the log entry second. These are two separate writes to the store, and a crash can fall between them:

A server stranded this way is a follower with an empty configuration. It never campaigns, because it isn't a voter in any configuration it knows. Bootstrapping it again fails with ErrCantBootstrap. In a bigger cluster this heals itself: the other servers elect a leader, whose replication gives the stranded one its log and configuration. It's permanent only where that server is needed for a majority, above all a one-server cluster, where nothing can ever be written again until someone deletes its data by hand. The window is a single write, once in a server's life, hence low severity.

After the fix the term is briefly 0 while the log holds an entry of term 1. That is harmless: the server's first election raises its term to 1, and the simulation's seed recovers exactly this way.

It's the same class of bug as Antithesis's #746: two related values saved as two separate writes, with a crash between them leaving a combination that the code then trusts.

How the simulation found it

  1. Found. The membership sweep under gray failure failed "the cluster recovers" on seed 54. That seed drew a single-voter cluster, and its one voter had a slow disk (fsync 38× slower), which stretched the gap between the two writes. A machine crash landed in it 28ms after start. The state dump showed the voter at term 1 with an empty log and no configuration, and the spares at term 0.
  2. Confirmed. With the writes swapped (a switch in the simulation build), the same seed recovers. TestBootstrapCrash then reproduces it directly, with no timing involved: a store whose log write fails after the term was saved, holding exactly what such a crash leaves.

Ready to submit

Branch fix/bootstrap-crash on your fork, based on upstream main, swaps the two writes and adds TestBootstrapCluster_CrashBetweenWrites. It crashes at each point (a store whose write fails), restarts the way applications do (bootstrap unless there's existing state), and requires the server to become leader and apply a command.

3. A demoted leader shuts down

Behaviour, not safetyPossibly intended: a question for upstream

What happens

Membership has two ways to take a server's vote away: RemoveServer takes the server out of the cluster, and DemoteVoter keeps it in as a non-voter (it keeps receiving the log, but doesn't vote or count towards a majority). When the server being demoted is the leader, raft treats the two the same. Once the configuration that takes its vote is committed, the leader steps down, and with ShutdownOnRemove (on by default) it shuts its raft down entirely:

// leaderLoop, when a new configuration commits
if !hasVote(r.configurations.committed, r.localID) {
	stepDown = true
}
...
if stepDown {
	if r.config().ShutdownOnRemove {
		r.logger.Info("removed ourself, shutting down")
		r.Shutdown()

hasVote is false for a removed server and for a demoted one alike. The configuration still lists the old leader as a non-voter, but it no longer runs. A demoted follower keeps running as a non-voter, as you'd expect.

Why it might matter

  • The option's own documentation speaks only of removal: "If we are a member of a cluster, and RemovePeer is invoked for the local node … If ShutdownOnRemove is set, we additional shutdown Raft." Demotion isn't mentioned.
  • An operator who demotes the current leader expects a non-voter that keeps up with the log, and gets a dead process instead. The cluster lists it as a member, but it never catches up. Promoting it again later adds a voter that never answers, which can cost the cluster its majority. That is how the simulation's operator stalled clusters.
  • It isn't a safety problem: the rest of the cluster carries on correctly.

How it came up

The simulation's membership operator demoted leaders, and sometimes later tried to promote them again. Those clusters stalled, and the trail led here: raft's log showed removed ourself, shutting down on a server that was meant to stay a non-voter. The operator now skips servers whose raft has shut down. The behaviour is noted in the issue draft as a question, since it may be deliberate.

Full results, including every sweep and the bug benchmark, are in DST.md on the fork's dst branch. The simulation is go-dst-kit.
